# Passkey backup ("Face ID ile yedekle"): design

Decided with Behlül on 2026-10-19: the recovery code is reliable but tedious (copy it, keep it, paste it). A
passkey does the same job with one Face ID tap, is kept in iCloud Keychain, and also works in Safari next to the
home-screen app (today those two keep separate device accounts). Option (a) was chosen: a device that comes back
with a passkey gets its own silent sign-in, so it never asks for Face ID again and no other device is affected.
The recovery code stays as the backup of the backup.

## Changed after review (built on `feature/passkey`)
- "New code" deletes passkeys too (it is the lockout for a lost device); a passkey sign-in racing it gets 401.
- Device secrets: at most 20, evicting the least recently used (`last_used_at`, V13), not the oldest created.
- Anonymous auth endpoints are rate-limited per client (30 a minute, 429 + Retry-After), and live sign-in
  ceremonies are capped at 500.
- Options carry `expiresAt`; the web app prefetches them before the tap and refreshes them, because Safari opens
  Face ID only inside the tap's user activation.
- A device that came back through a passkey holds a device secret, so it never shows that as a recovery code.

## How it works (for the interview)
- **WebAuthn / passkey:** the phone makes a key pair. The private key never leaves iCloud Keychain; the server
  stores only the public key. To sign in, the server sends a random challenge, the phone signs it after Face ID,
  and the server checks the signature with the stored public key. Nothing secret travels or is stored on the
  server, so a database leak reveals nothing usable.
- **Discoverable credential:** the passkey carries a user handle, so signing in needs no email or username: the
  phone offers "LiftLog" and the server maps the handle back to the account.
- **Device secrets:** after a passkey sign-in the phone makes a fresh random secret and the server keeps its
  BCrypt hash as an extra password of that account. The phone then signs in silently with it, exactly like a
  device that never lost its data. "New code" (change password) still signs everyone out: it also deletes all
  device secrets.

## Backend
Library: `com.yubico:webauthn-server-core` 2.10.1 (RelyingParty, start/finish registration and assertion).

Migration V12:
- `users.passkey_handle BYTEA UNIQUE` (32 random bytes, set on the first passkey).
- `passkeys (id BIGSERIAL PK, user_id → users ON DELETE CASCADE, credential_id VARCHAR(1024) UNIQUE (base64url),
  public_key_cose BYTEA, signature_count BIGINT, created_at, last_used_at)`.
- `webauthn_ceremonies (id UUID PK, kind VARCHAR(16) CHECK IN ('REGISTER','LOGIN'), user_id → users nullable,
  request_json TEXT, expires_at)`: the options of a started ceremony, single use (deleted when finished),
  5 minutes. Kept in the database so a restart or a second instance does not break a ceremony in progress.
- `device_secrets (id BIGSERIAL PK, user_id → users ON DELETE CASCADE, secret_hash VARCHAR(100), created_at)`;
  at most 10 per user, the oldest are dropped.

Relying party: origins = `liftlog.cors.allowed-origins`; RP id = host of the first origin, overridable with
`liftlog.passkey.rp-id`. No new environment variables on Render (CORS_ALLOWED_ORIGINS is already the web URL).

Endpoints (JSON; `publicKey` is exactly what `navigator.credentials` needs, binary values as base64url):
- `POST /api/v1/profile/passkeys/options` (JWT) → `{ceremonyId, publicKey}` creation options (resident key
  required, user verification required, attestation none, excludeCredentials = the user's passkeys).
- `POST /api/v1/profile/passkeys` (JWT) `{ceremonyId, credential}` → 201 `{id, createdAt}`. 400 for a bad or
  expired ceremony or a credential that fails verification.
- `GET /api/v1/profile/passkeys` (JWT) → `[{id, createdAt, lastUsedAt}]`.
- `POST /api/v1/auth/passkey/options` (anonymous) → `{ceremonyId, publicKey}` request options (no allow list,
  user verification required).
- `POST /api/v1/auth/passkey` (anonymous) `{ceremonyId, credential, deviceSecret}` → `AuthResponse`. The
  deviceSecret (base64url, 43 characters, generated by the phone) is stored as a device secret. 401 when the
  assertion does not verify or the passkey is unknown.
- `/auth/login` accepts the password or any device secret. `PUT /profile/password` accepts either as the
  current password and deletes all device secrets.
- No extra rate limiter on the anonymous endpoints: an assertion cannot be guessed, and options only create a
  short-lived row (expired rows are deleted whenever a new ceremony starts).

## Web
- `lib/webauthn.ts`: base64url ↔ ArrayBuffer, options JSON → `navigator.credentials` options, credential →
  JSON (no reliance on `parseCreationOptionsFromJSON`, which older iOS versions lack). `passkeysSupported()`.
- Profile: a "Yedek" card at the top of the recovery area: "Face ID ile yedekle" until a passkey exists, then
  "Yedeklendi · 19 Eki". The recovery code moves below it, collapsed ("Kurtarma kodu — yedeğin yedeği").
- Workouts banner: only while there is no passkey (and the code was never saved); its button creates the passkey
  directly (one tap + Face ID). Gone for good once a passkey exists. "Sonra" snoozes 30 days.
- Welcome and signed-out screens: "Face ID ile geri dön" next to "Kurtarma kodum var". On success the device
  stores `{email, password: deviceSecret}` and reloads, like a code restore.
- Without WebAuthn support everything falls back to today's recovery code UI.

## Tests
- Backend: a software authenticator in the tests (EC P-256 key, CBOR attestation "none", signed assertions)
  drives the real endpoints: register, list, sign in with a fresh device secret, silent login with that secret,
  wrong signature 401, reused or expired ceremony 400, another user's passkey cannot be registered twice,
  "new code" deletes device secrets.
- Web: webauthn conversions, the passkey restore flow in session.ts with a stubbed `navigator.credentials`,
  Profile/banner states.
